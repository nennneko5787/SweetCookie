# 0002 — 実装計画と、実際に決めたこと

## 層

| 層 | もの |
|---|---|
| `core/format` | `BlockGeometry` — Path A の述語と、Java モデル JSON の生成 |
| `core/format` | `BlockModels.geometryOf` — コンポーネントからモデル識別子を取り出す |
| `core/format` | `AddonIrJson` に状態ごとの `model` 投影 |
| `src/main/java` | `BlockBinding.appearanceOf` — 識別子解決・テクスチャ解決・フォールバック |
| `src/main/java` | `BoundBlocks.Appearance` — 状態ごとのモデル JSON と、それが名指すテクスチャ |

**変換の算術はすべて `core`。** Minecraft 側に残るのは「バインド時に組み立てて配信する」だけ。
座標のオフセット、UV の除数、inflate、mirror — 間違えうるものが全部
ミリ秒で回るテストの側にある。

## Path A / Path B の述語（SC-150 §5.1 に確定）

モデル全体で以下がすべて成り立つときに Path A。ひとつでも崩れたら Path B。**部分的な変換はしない。**

1. `binding` を持つ bone がない（Molang による親付け替え）
2. `poly_mesh` / `texture_meshes` がない
3. **bone の回転がすべてゼロ**
4. cube の回転がゼロ、または 1 軸 ±22.5/±45

3 について: 90 度の倍数は軸と面名を同時に置換すれば原理的には変換できる。**claim しない。**
面の置換を間違えると「輪郭は正しくテクスチャだけ違う」モデルになり、見つかるまでの間ずっと
テクスチャのバグに見えるため。

4 の角度集合は Minecraft 自身のモデルローダーが検証している値。外れた値を出すとモデル全体が
読み込みで拒否され、**ブロックが一切描画されなくなる**。だから出す前に弾く。

## フォールバック（SC-150 §5.2）

3 通りの失敗（モデルが無い / 述語が弾いた / Path B が未実装）はすべて
**`*` のテクスチャを貼った単なる立方体** になる。これは今まで全ブロックがそうだったものと同じで、
つまり Path A は既存動作の純粋な上積み。診断は 2 種類に分けた:

- `SCE-2030` パックが宣言していないモデルを指している → 直すのは作者
- `SCE-2031` モデルはあるがこのビルドが描けない → 直すのは我々

1 つのコードにまとめると全員が同じ間違ったページに送られる。

## 遮蔽（SC-150 §5.5）

プールブロックを **`noOcclusion()`** で登録する。ブロックより小さいモデルが隣のブロックの面を
カリングしてはならず、小さいかどうかは登録時には分からない — 遮蔽形状は
バインド前に 1 度だけ焼かれ、当たり判定と違って `dynamicShape` に相当する逃げ道がない。

代償: 立方体のブロックが光を遮らなくなる。**軽くて見えるまずさ（洞窟が明るい）** と
**重くて分かりにくいまずさ（カスタムモデルの向こうの地形が消える）** の取引で、前者を取った。

## 途中で見つけて直したバグ

生成アセットの名前が **サイズクラスだけ** から作られていた（`block/16_0`）。同じクラスの
2 つのブロックが同じモデルファイルを書き、後勝ちで **片方のアドオンのブロックが
もう片方のモデルとテクスチャを着る**。スロット単位の名前に変えた。

症状が出るのは「同じサイズクラスの 2 つ目のブロック」＝ 誰でも 2 つ目に入れるアドオンで、
今回カスタムモデルを入れるまで全部が同じ立方体だったので見えなかった。
