## 装備スロット — 「読めない」という記録が誤りだった

以前この文書に「レンダーステートから装備品が読めないので装備スロットの attachable は

## 座標系は 3 度目にして初めて「解いて」出した

`IN_FIRST_PERSON` は画面を見る前に紙の上で決まった。プレイヤーが南を向いた状態に固定して
軸に名前を付けると、両辺とも既知になる:

```
Bedrock -> world     R(180) . scale(-1,-1,1) . ON_PLAYER   =  diag( 1,  1, -1) / 16
world   -> camera    カメラの -Z が南、+X が西              =  diag(-1,  1, -1)
Bedrock -> camera                                          =  diag(-1,  1,  1) / 16
```

検算になるのが `position: [0,0,-11]`。この式に通すとカメラの 0.69 ブロック前方に落ち、
`AddonSurvey` の測定値と一致する。**式と測定が独立に同じ数を出した**ので、実機を起動する前に
確からしさが分かった。

パリティは奇数（1 軸反転）で、これは ② 'で**バグだった**のと同じ形だが、ここでは正しい。
Bedrock のモデル空間はもともとワールドに対して鏡像で、world→camera は真の回転だから、
合成は鏡像のままでなければならない。**「1 軸反転は常にバグ」ではなく、両辺を書けば決まる。**

## 実機で見つかった 2 件（どちらも 1 箇所）

**① 高さの符号が逆。** Java のエンティティ空間は **+Y が下**。`translate(0, -24/16, 0)` は
「上へ 1.5 ブロック」で、必要なのは下へ 1.5 ブロックだった。**補正が欠けている上に逆方向へ
同じ量**動かしたので合計 3 ブロック浮いた。定数に `BEDROCK_FLOOR` と名前を付けた。

**② 座標系の取り違え。** 頂点生成器が**座標系を 1 つしか持っていなかった**のが根本原因。
アイテムとして描く空間とプレイヤーの一部として描く空間は別物なのに、先に書いたアイテム用の
変換（ブロック由来の Z ミラー）を、後から書いたレイヤーがそのまま継承していた。両版とも
エンティティモデルは −Z を向くので、Z を反転すると**プレイヤーと反対を向く**。

呼び出し側が選ぶ形に変えた:

```java
AttachableGeometry.AS_ITEM   = {1/16, -1/16, -1/16}   // vanilla のトライデントと同じ
AttachableGeometry.ON_PLAYER = {1/16, -1/16, +1/16}   // Z は反転しない
```

**教訓として残す**: 「1 つの変換定数」は、2 つ目の呼び出し側が現れた瞬間に嘘になる。

**②' 反転する軸の数を間違えた（同じ定数、別のバグ）。** 向きを直したあと `ON_PLAYER` は
`{+1, -1, +1}` — **1 軸だけの反転**だった。1 軸の反転は座標系の利き手を裏返すので:

- モデルが左右鏡像になる（対称なキャラでは気づきにくい。銃が反対の腕に付く）
- **X と Z 回りの回転の向きが全部裏返る** → 脚の `rotation: [-73, 24, 6]` が反対に振れる

報告は「足が逆方向にいってる」だった。**アニメーションのバグに見えて、実際はパリティのバグ。**
回転の計算は最初から正しく、空間の利き手が裏返っていただけ。

vanilla が `scale(-1, -1, 1)` と 2 軸反転しているのはこのため（偶数回なら利き手が保たれる）。
その片方だけを写していたので、**両方写さないより悪かった**。

正しい値は推測ではなく解いて出す:

```
レイヤーの空間:  world = (-mx, -my, mz)     ← vanilla の scale(-1,-1,1) の中にいる
Bedrock の空間:  world = ( bx,  by,  bz)
∴ mx = -bx, my = -by, mz = bz    →  {-1, -1, +1}
```

`AS_ITEM = {1,-1,-1}` は最初から 2 軸だったので無事だった。

もう起きない。SC-180 §3.4.1 に規範として書いた。

**④ 誤診して入れた変更が、診断の訂正後も残っていた。**

③ の「脚が逆」に対し、パリティの議論で `ON_PLAYER` の X を反転させた。真因は回転の向きで、

Minecraft には利き手設定があり、左利きのプレイヤーではメインハンドが左手になる。
右利きでは症状が出ないので、**指摘されるまで気づけない**種類の誤り。`state.mainArm` を見る。

## 測定ツールを足した

`AddonSurvey` に `geometry.<名前>` を渡すと、ボーンごとの姿勢後の座標範囲を出す。

「無いのか、別の場所にあるのか」は**画面上では同じに見える**。足と銃が「描画されていない」と
報告されたとき、これで 26 ボーン 122 cube すべてが正しく計算されていることが分かり、
原因を配置の側に絞れた。

**③ 厚さ 0 の cube を 2 枚描いていた。** Bedrock のモデルは目・髪・ヘイロー・スカートの布を
「1 軸が `size: 0` の cube」で書く。6 面すべてを出すと、その軸の 2 面が**完全に同じ平面**に
重なり、深度バッファを奪い合う。

画面上は面がちらつく（ティアリング）ので**レンダラの精度問題に見える**が、実際は数え間違い —
1 つの面を 2 回描いていた。報告してくれた人も「統合版より Java のレンダラが高性能だから？」と
疑っていた。そう見えるのが厄介なところで、書き残す理由でもある。

厚さの判定は inflate 込み。`0.001` のような薄い箱は本物の箱として 6 面のまま残す
（丸めると、誰かが描いた面を黙って落とすことになる）。

## 一人称を実機で回した日に見つかったもの

実機で人に見てもらうと、**コンパイルもテストも通る間違い**が次々に出た。順に:

| 報告 | 真因 |
|---|---|
| 一人称でモデルが飛ぶ | 合成規則。ただし**真因は角度規約の Y**（下記） |
| 脚の開きが狭い | 開きが狭いのではなく**内側へ交差**していた。Y の角度規約 |
| 横だけ向きが違う | 同上。Y だけ逆だったので上下は合っていた |
| 左腕が銃を構えない | 同上。左右を分けているのは Y の +28.65 だけ |
| ヘイローが頭に追従しない | `head` という名のプレイヤー骨格ボーンを束縛していなかった |
| 装備してもモデルが出ない | `equippable` に asset id が無く `headEquipment` が空だった |
| 手に持つと防具のモデルが出る | 装備品の手のコンテキストまで空にしていた |
| 顔の向きがずれる | 一人称だけ `target_y_rotation` に**絶対**の向きを渡していた |
| 視点で脚が動く | 脚は動いていない。カメラと違う（補間前の）角度で打ち消していた |
| ホシノだけ一人称でずれる | `body` の束縛が**置き換え**でなく掛け合わせだった |

**Bedrock の角度規約は全軸共通ではない。X と Z だけ逆で、Y は逆でない。**
これは Java↔Bedrock が Y 反転の関係であることの帰結で、反転した軸が関与する 2 軸だけが
逆になる。X の反転は「脚が後ろへ振れた」で実証されていたが、**Y は同時に、
「符号規約は全軸共通だろう」という理由だけで反転され、誰も検算しなかった**。

`BoneMatricesTest` の該当アサーションは**二度ともコードに合意していた**（最初は −1、
X 修正のときに +1、どちらも検算なし）。SC-180 §3.4.1 に
**「1 軸で正しい補正は他の軸の証拠にならない」**として書いた。

## 合成規則で 4 回目をやりかけた

「横へ飛ぶ」を説明するために入れた**後勝ち**規則は、真因（Y の角度規約）を直した時点で
**根拠が消えていた**のに、再検証されず残っていた。ここまでは 3 回目の同じ失敗。

まずいのはその後始末で、**「Bedrock の既定は加算合成だから」という理屈だけ**で、
ユーザーが実機で確認済みの規則を上書きした。結果:

- シロコが**前に出て正面を向いた**（`.hand` の `root3: rotation [0,180,0], position [0,0,-11]`）
- ホシノの**首が肩から外れた**（`head2` の `position [8,4,0]`）

戻した。SC-180 §4.1 に**この位置に入った規則 3 つと画面での見え方**を表で残し、
**「理屈だけで置き換えるな。この規則が外す実際のフレームを持ってこい」**と規範に書いた。

3 つとも「目の前のスクリーンショットを説明できたから」採用されている。**症状 1 つから
逆算した規則は、発見ではなく仮説。**

## 測定器が届いていないと、バグは構造的に見えない

合成のバグが長く残ったのは、`AddonSurvey` が **アニメ 1 本しか姿勢化できなかった**から。
バグは複数本の合成にあり、道具の側が原理的に見られなかった。3 つ足した:

- `attachable.<識別子> [first|third]` — **視点として**姿勢化（`scripts.animate` 全部、条件も評価）
- `UNREADABLE:` 行 — コンパイルできなかった Molang（`unreadableExpressions()` は前からあった）
- `AttachableContext` を `core` へ — Minecraft 型を 1 つも持たないのに `src/main` にあり、
  測定器がレンダラと同じ文脈を作れなかった

## 選択肢で聞くと速い

「顔の向きがおかしい」だけでは動けなかった。**「追従するがずれる／上下が逆／左右が逆／固定」
＋「どの視点か」**を選んでもらったら、*一人称のみ・追従はする* の 2 条件が原因を 1 点に
絞った（絶対 yaw を渡していた）。推測 3 回より速い。

**統合版の挙動を直接聞くのも同じ。**「三人称で首は回るか」への「回る」が、
`query.target_*` が 0 でないことを一発で確定させた。

## 分かったこと

**Molang は書かなくてよい。** `core/molang` にパーサ・クロージャ生成・math・スコープ付き
コンテキストが既にある。カバレッジが全部 `stub` なのは「実行時に誰も評価していない」から
であって、言語が無いからではない。段階 D はエンジンを繋ぐ作業であって言語実装ではない。

**サブミット経路も試作がある。** `BedrockCubeSubmitter` が 4 ノードでコンパイルでき、
`submitCustomGeometry` の署名が両バージョンで同一。レンダラの抽象化は要らない。

**Path A は使えない。** おんぶシロコのボーンは 22.5° / −17.5° / 35° / −45° の自由角度で、
Java の `elements` は 1 軸・±22.5/±45 しか持てない。自前で頂点を出す以外にない。

## まだ確認していないこと

**巻き順と UV の向き。** 試作の docstring が自分で「コンパイラでは決まらず、描画された画像
でしか分からない」と書いている。段階 A の最初の起動で確定させる。

**座標系。** ブロックで確定した「Z ミラー・X は +8」は**ブロックの話**。エンティティ空間は
原点が足元でピクセル単位なので、同じとは限らない。段階 A で 1 回確かめて `spec.md` に書く。
