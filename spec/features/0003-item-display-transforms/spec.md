# 0003 — `item_display_transforms`

対象カバレッジエントリ:

- `geometry/item_display_transforms`（新設、`spec/coverage/rp-geometry.yaml`）

対応する normative: SC-180 §3.6（新設）、SC-150 §5.6（新設）。

## きっかけ

0002 の実クライアント確認で、**ワールドに置いたブロックは正しく、ホットバーのアイコンだけ向きが
違う**という報告が出た。手持ちのモデルは正常。

アイコンと手持ちは **同じモデルファイル**を別の角度から描いたものなので、片方だけが鏡像になることは
原理的にありえない。つまりモデルの変換ではなく、**描くときの姿勢**の問題だと分かる。

実際のアドオンの geo ファイルにこれが入っていた:

```jsonc
"item_display_transforms": {
  "gui": {
    "rotation": [32.95, -47.55, 2.29],
    "translation": [-1, -1.25, 0],
    "scale": [0.5, 0.5, 0.5]
  },
  "firstperson_righthand": { ... },
  ...
}
```

transpiler はこれを読まずに捨て、`parent: minecraft:block/block` が持つ Java 既定値
（`gui` は `[30, 225, 0]`）で描いていた。作者指定の約 -47° とはおよそ 4 分の 1 回転ずれ、
見えている 2 側面が入れ替わる。これが「逆に見える」の正体。

## Bedrock 側の挙動

geo ファイルの **モデル直下**（`bones` の兄弟。`description` の中ではない）に置く。
コンテキストごとに `rotation` / `translation` / `scale` を指定する。

## Java 側で何が違うか

**ほとんど違わない。** Java のモデル JSON の `display` が同じもので、

| | Bedrock | Java |
|---|---|---|
| キー名 | `item_display_transforms` | `display` |
| コンテキスト名 | 8 つ | **同じ 8 つ** |
| フィールド | `rotation` / `translation` / `scale` | **同じ 3 つ** |
| 単位 | 度 / 1/16 ブロック / 倍率 | **同じ** |

Bedrock が Java から概念ごと持ってきたため、対応表を間違える余地がない。作業は SC-150 §5.3 の
座標変換を適用することだけ。

- `rotation`: モデル自身の回転と同じ補正（§5.1 rule 3 の角度の向き + Z ミラー）。x と y は
  2 回反転して打ち消し合い、z だけ反転する。
- `translation`: **位置ではなく変位**。Z ミラーの符号は付くが、中心→角の +8 は付かない。
- `scale`: そのまま。ミラーは軸方向のスケールと可換。

## 観測していないこと

**3 軸の合成順序。** Java は X → Y → Z の順に読む。Bedrock も同じだと仮定している。
ミラーによる共役は合成順序を保つので、**1 軸だけの回転はどちらでも正しい**。2 軸以上を同時に
回す transform だけが差を出しうる。今回のトロフィーは 3 軸すべて非ゼロなので、ここが違えば
まだ少しずれる。

**パックが書かなかったコンテキスト。** Java は `display` を親チェーンに沿ってコンテキスト単位で
解決するので、書かなければ `minecraft:block/block` の答えが残る。Bedrock 側の既定値と
`block/block` の値が一致するかは比較していない。恒等変換を書き込むと vanilla の答えを
「変換なし」で潰すことになるため、**書かない**方を選んだ。
